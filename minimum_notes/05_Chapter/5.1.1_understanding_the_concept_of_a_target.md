# Understanding the Concept of a Target... 
Essentially, it's a recipe that a buildsystem follows to compile a set of files into another file. So, the *target* outcome may be a set of **.o** file, the *target-logic* know that in order to build the set of **.o** files that it needs the **.cpp** files. Embedded within the *target-logic* is the commands to turn the **.cpp** files into **.o** files. When target execution occurs it would check, and make sure that all the **whateve.cpp** files were turned into **whatever.o** files. 

```cmake
add_executable(app1 a.cpp b.cpp c.cpp)
```
  
In CMake, we can create a target using these 3 commands:  
- add_executable()
- add_library()
- add_custom_target()  
  
Before building executables or libraries, CMake performs a check to determine whether the generated output is older than the source files. This mechanism helps CMake avoid recreating artifacts that are already up to date. By comparing timestamps, CMake efficiently identifies which targets need to be rebuilt, reducing unnecessary recompilation.  
  
All commands defining targets require the name of the target to be provided as a first argument, so it can be later referenced in other commands that do things with targets, like **target_link_libraries()**, **target_sources()**, or **target_include_directories()**.

## Defining executable targets... 
The command to define an executable target, **add_executable()**, is self-explanatory. 

```cmake
add_executable(<name> [WIN32] [MACOSX_BUNDLE] [EXCLUDE_FROM_ALL] [source1] [source2...])
```  
  
The following extensions are supported:

- For C: c, m
- For C++: C, M, c++, cc, cpp, cxx, m, mm, mpp, CPP, ixx, cppm, ccm, cxxm, c++m  
  
Note that we're not adding any **header files** to the source list. That can be done either implicitly, by providing a path to the directory where those files are with **target_include_directories()**, or by using a FILE_SET feature of the **target_sources()** command(added in CMake 3.23).  
  
## Defining library targets... 
Defining library targets is very similar to defining executables.  
```cmake
add_library(<name> [STATIC | SHARED | MODULE]
            [EXCLUDE_FROM_ALL]
            [<source>...])
```  
The only difference is the **STATIC**, **SHARED**, and **MODULE** keywords. These define what sort of artifact CMake will generate: statically linded libraries, shared(dynamic libraries), or modules.  
  
## Custom targets... 
Custom targets extend the build functionality beyond what CMake provides out of the box by executing explicitly given command lines; for example, they can be use to:
- Calculate the checksums of other binaries.
- Run the code sanitizer and collect the results.
- Send a compilation report to the metrics pipeline.  
```cmake
add_custom_target(Name [ALL] [COMMAND command2 [args2...] ...])
```  
  
Custom targets have certain drawbacks to consider. Since they invole shell commands, they can be system specific, potentially limiting portability. Additionally, custom targets may not provide a straightforward means for CMake to determine the specific artifacts or by products being generated, if any.  
  
Custom targets also doesn't provide the staleness check like executables and libraries(they don't verify whether the sources are newer than the binaries), because by default they're not added to the **dependency graph**(so the ALL keyword works in opposite to EXCLUDE_FROM_ALL). Let's find out what that dependency graph is about. 

## Dependency graph...   
  
**minimum_notes/05_Chapter/01-dependency_graph/CMakeLists.txt**
```cmake
cmake_minimum_required(VERSION 3.26)
project(BankApp CXX)

add_executable(terminal_app terminal_app.cpp)
add_executable(gui_app gui_app.cpp)
target_link_libraries(terminal_app calculations)
target_link_libraries(gui_app calculations drawing)

add_library(calculations calculations.cpp)
add_library(drawing drawing.cpp)

add_custom_target(checksum ALL
                  COMMAND sh -c "cksum terminal_app>terminal.ck"
                  COMMAND sh -c "cksum gui_app>gui.ck"
                  BYPRODUCTS terminal.ck gui.ck
                  COMMENT "Checking the sums... "
)
```  
  
We link our libraries with executables by using the target_link_libraries() command. Without it, the building of executables would fail because of undefined symbols. Have you noticed that we invoked this command before declaring any of the libraries? When CMake configures the project, it collects information about targets and their properties - their names, dependencies, source files, and other details.  
  
After parsin all the files, CMake will attemp to build a dependency graph. Like with all valid dependency graphs, they're **Directed Acyclic Graph(DAGs)**. This means that there is a clear direction of which target depends on which, and such dependencies cannot form cycles.  
  
When we execute cmake in build mode, the generated buildsystem will check what top-level targets we have defined and recursively build their dependencies. Let's consider our example from our dependency graph. 
1. Start from the to top sdand build both libraries in group 1. 
2. When the Calculations and Drawing libraries are complete, built group 2 - GuiApp and TerminalApp. 
3. Build a checksum target; run specified command lines to generate chechsums(cksum is a Unix checksum tool, which means that this example won't build on other platforms).  
  
There's a slight issue, though - the preceding solution doesn't guarantee that a checksum target will be built after the executables. CMake doesn't know that a checksum depends on the executable binaries being present, so it's free to start building it first. To resolve this problem, we can put the **add_dependencies()** command at the end of the file.
```cmake
add_dependencies(checksum terminal_app gui_app)
```
This will ensure that CMake understands the relationship between the checksum target and the executables.  
  
But... what's the difference between target_link_libraries() and add_dependencies()? target_link_libraries() is intended to be used with actual libraries and allows you to control property propagation. add_dependencies() is meant to be used only with top-level targets to set their build order.  
  
As projects grow in complexity, the dependency tree gets harder to understand. How can we simplify the process?

## Visualizing dependencies...  
Luckily, CMake has a great module to generate dependency graphs in the **dot/graphviz** format, and it supports both internal and external dependencies!  
  
To use it, we can simply execute the command:
```bash
cmake --graphviz=test.dot .
```  
  
The module will produce a text file that we can import to the Graphviz visualization software, which can render an image or produce a PDF or SVG file that can be stored as part of the software documentation.  
  
Custom targets are not visible by default and we need to create a special configuration file, CMakeGraphVizOptions.cmake, that will allow us to customize the graph. Us the set(GRAPHVIZ_CUSTOM_TARGETS TRUE) command to enable custom targets in your graph.  
  
**minimum_notes/05_Chapter/01-dependency_graph/CMakeGraphVizOptions.cmake**
```cmake
set(GRAPHVIZ_CUSTOM_TARGETS TRUE)
```  
  
Other options allow the addition of a graph name, a header, and node prefixes and configure which targets should be included or excluded from the output(by name or type). Visit the official CMake documentation for the CMakeGraphVisOptions full description of this module.

https://dreampuf.github.io/GraphvizOnline/  
  
All you need to do is copy and paste the contents of the test.dot file into the window on the left and your project will be visualized.
